# 2.1 — Atividades livres

## Escopo entregue

- Tela `/app/activities`: histórico paginado de atividades livres (corrida, futebol, natação…), com filtro por período (`De`/`Até`) guardado na URL
- Registro em modal: tipo, data e hora, duração (min), comentário e foto, tudo opcional exceto tipo e duração
- Criação de tipo personalizado direto no formulário ("Novo tipo"), já selecionado após criar
- Edição (tipo, data, duração, comentário, trocar/remover foto) e exclusão com confirmação em dois passos
- Item "Atividades" no menu (sidebar desktop e tab bar mobile) e atalho na home
- `GET /activity-types`, `POST /activity-types/custom`, `GET/POST /activities`, `PATCH/DELETE /activities/:id`, `POST /activities/:id/photo`
- `e2e/activities.spec.ts` (15 casos × desktop/mobile) + `e2e/navigation.spec.ts` atualizado

## Decisões técnicas

- **Modal único para criar e editar**, igual a exercícios (1.3): a atividade tem poucos campos, então não justifica página de detalhe própria. A linha da lista é um botão que abre o modal já preenchido.
- **Tipo personalizado criado inline**, não em tela separada: a API não tem edição/remoção de tipo, então uma tela de gestão só teria "criar". O campo vive dentro do formulário da atividade sem ser um `<form>` aninhado; `Enter` cria o tipo em vez de enviar a atividade. 409 do backend (nome repetido, sem diferenciar maiúsculas, inclusive contra os padrão) vira "Já existe um tipo com esse nome."
- **Tipos agrupados no `<select>`** com `<optgroup>` "Padrão" / "Seus tipos", usando o `source` da API. O select é controlado (`Controller`), porque na edição os tipos chegam depois do `reset` do formulário e um select não controlado perderia o valor.
- **Data e hora com `<input type="datetime-local" max={agora}>`**: o seletor bloqueia o futuro; o form usa `noValidate` e o Zod repete a regra, com mensagem inline. Na edição, `performedAt` só é enviado se mudou: o input tem precisão de minuto e reenviar o valor zeraria os segundos. Isso antecipa parte da 2.3 (registro retroativo); a 2.3 continua dona da integração com o calendário e da mensagem amigável para rejeição do backend.
- **Duração inteira de 1 a 1440 min**, espelhando o backend; campo vazio vira "Informe a duração" em vez de `0` (mesmo `z.preprocess` do perfil, 1.2).
- **Foto em duas chamadas**: `POST /activities` (ou `PATCH`) e depois `POST /activities/:id/photo`. Se só a foto falhar, a atividade fica salva e um toast avisa. Remover a foto existente manda `photoUrl: null` no `PATCH`; escolher outra substitui direto pelo upload.
- **`PhotoDropzone` e `compressImage` movidos para `shared/`** (`shared/ui/PhotoDropzone.tsx`, `shared/lib/image.ts`): eram da 1.5 e agora são usados por duas features. O backend não comprime e limita a 5 MB, então a imagem é reduzida para JPEG 1600px no cliente, como na sessão. O texto alternativo da prévia virou prop (`previewAlt`).
- **Filtros e paginação iguais ao histórico de sessões** (1.5): dia local convertido para ISO nos limites do dia, `page` na URL, 20 por página.

## Integrações de API consumidas

| Endpoint | Uso |
|---|---|
| `GET /activity-types` | Opções do select (padrão + personalizados) |
| `POST /activity-types/custom` | "Novo tipo" no formulário |
| `GET /activities?from=&to=&page=&limit=` | Lista, filtros, paginação |
| `POST /activities` | Registrar |
| `PATCH /activities/:id` | Editar; `photoUrl: null` remove a foto |
| `DELETE /activities/:id` | Excluir |
| `POST /activities/:id/photo` | Foto (base64, comprimida no cliente) |

`GET /activities/:id` não é usado pela UI (a lista já traz tudo); só pelos testes.

## Como testar

Pré-requisito: backend com a migration `add_free_activities` aplicada e `yarn db:seed` rodado (16 tipos padrão).

```bash
npx playwright test e2e/activities.spec.ts
```

| Caso | O que verifica |
|---|---|
| Estado vazio | título, contagem 0, mensagem |
| Registro | tipo padrão + duração + comentário; linha mostra "1 h 30 min"; data padrão = agora |
| Validações | tipo e duração obrigatórios, 0, 1441, data futura; nada é gravado |
| `max` do input de data | igual a hoje |
| Retroativo | data passada gravada com o horário escolhido |
| Tipo personalizado | criado inline, aparece em "Seus tipos" e já selecionado |
| Tipo repetido / vazio | 409 → mensagem; `Enter` não envia a atividade; cancelar |
| Edição | troca tipo e duração, limpa comentário (`null`), data intocada preservada |
| Exclusão | confirmação em dois passos |
| Foto | upload no registro; remoção na edição; arquivo não imagem rejeitado |
| Lista | ordem `performedAt desc` |
| Filtros | `De`/`Até`, persistência na URL após reload, vazio no período, limpar |
| Paginação | 21 itens → 2 páginas |

Resultado: 30/30 (desktop + mobile), 90/90 com `--repeat-each=3`. Suíte completa: 156 passed, 2 skipped.

## Pendências

- Sem edição/remoção de tipo personalizado: a API não tem essas rotas (ver `forma-server/sdd/2.1-atividades-livres.md`).
- Mídia antiga não é apagada no backend ao trocar/remover foto ou excluir a atividade (mesmo descope da 1.2/1.5).
- Atividades ainda não aparecem no calendário nem nos gráficos: entram na 2.2 e na 2.4.
