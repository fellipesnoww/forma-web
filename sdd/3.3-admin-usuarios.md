# 3.3 — Gestão de usuários (admin)

## Escopo entregue

- `/admin/users`: lista paginada (mais recentes primeiro), busca por nome/e-mail, abas Todos/Ativos/Inativos/Banidos/Admins, total de cadastrados.
- Perfil individual (`?user=<id>`, link direto): avatar, papel, status, estatísticas (treinos concluídos, atividades, planilhas, conquistas), último treino/atividade, cadastro, método de login, desafios, exercícios próprios, fuso.
- Ações com confirmação e **motivo opcional** (vai para o log de auditoria): desativar, reativar, banir; "Promover a administrador" só para super user.
- `GET /admin/users`, `GET /admin/users/:id`, `PATCH /admin/users/:id/status`, `PATCH /admin/users/:id/role`.

## Decisões técnicas

- **Regras da API espelhadas na UI**: admin só altera contas `user`; ninguém altera a própria conta; promoção exige alvo ativo e papel `user`. Os botões somem e uma frase explica o motivo. A API continua sendo a autoridade (403/409 viram toast).
- **Coluna "Último treino" do design removida da lista**: o resumo da listagem não tem esse campo (só o detalhe, em `stats.lastActivityAt`). Buscar o detalhe de cada linha seria N+1, então a informação fica no perfil.
- Aba "Admins" filtra `role=admin`. Super users aparecem em "Todos" e em `/admin/admins`.
- Selecionar usuário não reseta a página da lista (o `user` da URL não é filtro).

## Como testar

`npx playwright test e2e/admin/users.spec.ts` — perfil + estatísticas, link direto, desativar com motivo (conferido no audit log) e reativar, banir (o token do alvo passa a dar 403), cancelar não altera, abas de status, regras de admin (outro admin, própria conta, sem "Promover"), super user promove (alvo acessa `/admin` sem relogar).

## Pendências

Nenhuma.
