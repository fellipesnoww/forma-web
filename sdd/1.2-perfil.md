# 1.2 — Perfil do usuário

## Escopo entregue

- Tela `/app/profile`: nome de exibição (edição), avatar (upload), medidas corporais (peso, altura, cintura, peitoral)
- Histórico de medidas: lista + sparkline SVG de peso (sem lib de gráfico — ver decisões)
- Validação client-side espelhando o backend (`z.coerce.number().positive()` — valores > 0)

## Decisões técnicas

- **Avatar: `POST /media` (real) + `PATCH /profile` (ainda não existe)** — o roadmap original previa um endpoint dedicado `POST /profile/avatar`, mas o artifact de referência da API real documenta o fluxo como genérico: upload via `POST /media` (que já funciona hoje) devolve `{ id, url, ... }`; esse `url` é então persistido em `Profile.avatarUrl` via `PATCH /profile`. Segui o fluxo real (mais correto), não o do roadmap desatualizado. Como `PATCH /profile` não existe ainda, o upload funciona mas a persistência falha — erro tratado via toast, sem crash.
- **`AuthedImage` (`shared/ui/AuthedImage.tsx`)** — `GET /media/{id}` exige header `Authorization: Bearer`, que um `<img src>` comum não envia. Criei um componente que busca o binário via `fetch` autenticado e converte para blob URL. Sem isso, nenhum avatar jamais apareceria quando o backend estiver pronto.
- **Sparkline sem Recharts** — só 1 gráfico simples de linha (peso), phase 2 é que formaliza gráficos com Recharts (`ResponsiveContainer`, filtros de período). Implementar uma dependência de charting inteira para um sparkline seria desproporcional agora.
- **Nenhuma camada de persistência local paralela (localStorage) para medidas** — diferente do onboarding (flag trivial), CRUD completo de medidas em localStorage seria infraestrutura especulativa (o roadmap já reserva modo offline completo pra Fase 6). A tela chama os endpoints reais e mostra estado de erro/vazio enquanto eles não existem.

## Como testar

1. `/app/profile` deve carregar sem crashar mesmo com backend parcial (mostra "Histórico ainda não disponível").
2. Editar nome + salvar → toast de erro (endpoint 404) até `PATCH /profile` existir; UI não quebra.
3. Upload de avatar → upload em si funciona (`POST /media` 201), toast de erro na etapa de persistir `avatarUrl` (esperado).

## Pendências — bloqueadas no backend

`PATCH /profile`, `GET/POST /profile/measurements` não existem no servidor (confirmado no artifact de referência da API — só Auth e Media estão "done" na seção "What's not built yet"). UI está pronta e tipada para esses contratos; funcionará sem mudanças assim que o backend publicar essas rotas.

## Correções posteriores (encontradas pela suíte E2E)

- Avatar agora usa `POST /profile/avatar`; o fluxo antigo (`POST /media` + `PATCH /profile { avatarUrl }`) recebia 400.
- Cintura/peitoral vazios não bloqueiam mais o registro de medida (`""` era coagido para `0`).
- Histórico de medidas lê `{ items }` com `createdAt`, como a API devolve; antes a lista nunca aparecia.

Cobertura: `e2e/profile.spec.ts`. Detalhes em [testes-e2e.md](testes-e2e.md#bugs-encontrados-e-corrigidos).


## Refatoração pelo design (`Forma Web.dc.html` · "Perfil")

Telas "Perfil · dados físicos e histórico de medidas" (desktop) e "Perfil · responsivo" do projeto de design.

- **Layout:** desktop em duas colunas (cartão de identidade 320px + dados/histórico); mobile em coluna única, com o cartão de identidade horizontal (avatar 68px, lápis de edição).
- **Edições em modal:** "Editar perfil" (botão no cabeçalho em `sm`+, lápis no cartão no mobile) abre o nome de exibição; "Registrar medidas" abre o formulário de medidas. O formulário é montado a cada abertura em vez de resetado num efeito: o reset por efeito às vezes rodava depois do primeiro campo preenchido e o apagava (falha intermitente na suíte).
- **Dados físicos:** 4 blocos (peso, altura em metros, cintura, peitoral) com os valores atuais de `GET /profile` (cada campo é o último informado), "Última atualização em …" pela medida mais recente. `—` quando não há valor.
- **Histórico:** tabela DATA/PESO/CINTURA/PEITORAL em `sm`+, com a linha mais recente destacada ("· atual"); no mobile, uma linha por medida ("64,2 kg · 71 cm · 92 cm"). Mesma marcação nos dois tamanhos (sem duplicar texto). Números em pt-BR (`64,2`).
- **Sparkline mantido** no cabeçalho do histórico: o design não tem gráfico, mas o item 1.2 do roadmap pede "lista + gráfico simples".
- **Fora do escopo agora** (estão no design, mas dependem de fases futuras ou de dados que a API não expõe): streak "12 dias seguidos" (4.3), cartão de conquistas (4.1), "desde mar 2026" (sem data de criação da conta na API) e o lápis para editar uma medida (não há `PATCH` de medida).
- **Correção:** o grid de coluna única crescia com o e-mail longo e criava rolagem horizontal no mobile; agora usa `grid-cols-[minmax(0,1fr)]`. Coberto em `e2e/profile.spec.ts`.

Novo: `profileApi.get` (`GET /profile`), tipo `ProfileDetails`, `lib/format.ts`.
