# 3.2 — Gestão de exercícios (admin)

## Escopo entregue

- `/admin/exercises`: catálogo com inativos, busca, filtro por grupo muscular e por status, totais "N ativos · M desativados", switch de ativação por linha.
- Cadastro/edição no painel lateral (desktop) ou modal (mobile): nome, grupo, imagem (envio, troca, remoção) e "Disponível no app" (só no cadastro).
- Modal "Grupos musculares": lista com contagem, criação (slug opcional, validado) e edição de nome/slug.
- `GET/POST/PATCH /admin/exercises`, `PATCH /admin/exercises/:id/status`, `GET/POST/PATCH /admin/muscle-groups`.

## Decisões técnicas

- **Campos do design sem contrato na API ficaram de fora**: "Categoria" (composto/isolado) e "Descrição" não existem no backend. "GIF" também não: a API aceita só JPEG/PNG/WebP.
- **"Disponível no app" no cadastro** (não está no design): a API aceita `isActive` na criação. Permite montar o exercício (imagem etc.) antes de publicá-lo, e os testes criam exercícios inativos para não alterar o catálogo que as specs de usuário contam em paralelo.
- **Imagem**: arquivos até 1,5 MB vão como estão (preserva transparência de PNG/WebP); maiores passam por `compressImage` (JPEG). O `<input>` não usa `capture`: o admin escolhe arquivos existentes.
- **Totais do cabeçalho** vêm de duas consultas `limit=1` (`status=active`/`inactive`), independentes dos filtros.
- **409 de nome** vira erro inline no campo, não toast.
- Invalidações cobrem também `['exercises']`, a biblioteca do usuário.

## Como testar

`npx playwright test e2e/admin/exercises.spec.ts` — totais, cadastro com grupo + imagem, nome obrigatório/duplicado (ignora maiúsculas), edição, switch + filtro de status, filtro por grupo, grupos musculares (slug inválido, slug derivado, renomear), entrada no log de auditoria.

## Pendências

- Sem exclusão de grupo muscular nem de exercício: a API não tem essas rotas (desativar é o caminho).
- Grupos criados pelos testes ficam no banco de dev (não há DELETE).
